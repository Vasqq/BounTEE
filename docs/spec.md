# Spec: BounTEE

Final spec, Nov 4, 2026. The requirements it delivers are in [requirements.md](requirements.md), referenced by ID throughout; the vocabulary is [GLOSSARY.md](../GLOSSARY.md); the decisions are [docs/adr/](adr/) (0001–0015). Where this spec and requirements.md differ, requirements.md wins.

## Problem Statement

**Protocols.** A Protocol's security lead running a bug bounty spends their time triaging reports, most of which don't reproduce, and AI now writes them for free. Meanwhile AI agents have made working exploits cheap to find (about $1.22 per agent run in Anthropic's SCONE-bench), for whitehats and attackers alike. When a real exploit does arrive, the Protocol's contracts on every chain stay exposed until someone reads the report and acts, and the report itself is a public pointer to the bug.

**Whitehats.** A whitehat, or the AI agent they run, who finds a working exploit has to hand it over before being paid. After that they have no leverage: severity can be downgraded and payment disputed or delayed. Immunefi calls its mediation "a strong recommendation and not a final verdict"; programmes allow up to 30 business days to pay; cases on record include $50k offered against a $500k maximum.

## Solution

A Protocol signs in with the MetaMask wallet it already uses, grants BounTEE the pause role on each covered contract (which proves it controls them), and posts a bounty on NEAR: a fixed amount of USDC, a minimum theft, an end date, and the covered contracts on Base and Arbitrum.

A Whitehat runs `bountee init` (on testnet it creates and funds a NEAR account with no sign-up), writes an exploit as a Foundry script, tests it locally against the contracts as they are now with the exact rule that will judge it, and claims from the terminal. The exploit is sealed on their machine. OutLayer replays it inside an Intel TDX enclave against the proof chain's state at a recent block, which the claim proves and the enclave confirms. If fresh accounts walk away with at least the minimum theft taken from the covered contracts, NEAR Chain Signatures signs a pause for every covered contract on every chain, the Whitehat is paid the whole bounty in seconds, and the Protocol can open the exploit. Anyone can deliver the signed pauses; NEAR's MPC network then confirms each one landed, and the bounty contract records it on NEAR. After a disclosure delay the exploit is published, so anyone can re-run it.

Nobody holds a key to the bounty: not the Protocol, not the Whitehat, not us. Junk claims cost the Protocol nothing. An AI agent can claim with a key that can only file claims. Everything is checkable from public data, with no keys and no funds.

## User Stories

**Protocol (security lead)**

1. As a security lead, I want to see a finished bounty before posting, so that I know what posting commits me to.
2. As a security lead, I want to sign in with the MetaMask wallet I already use, and use it both to grant pause roles and to post, so that I never need a separate NEAR wallet.
3. As a security lead, I want to see each pause-role grant I still need to make, chain by chain, and send it from MetaMask, so that setup is clear and I know when I'm done.
4. As a security lead whose contracts are administered by a multisig, I want to copy each pause-role grant into it, so that I can grant from where our admin rights actually live.
5. As a security lead, I want to be told in plain words why each chain needs a few cents of pause gas, that nobody can take it back, and that nobody presses the pause button, so that I fund it without worry.
6. As a security lead, I want to be told exactly how much NEAR my account needs for fees and where to send it, so that a chain I've never used doesn't stop me.
7. As a security lead on mainnet, I want to fund my bounty with USDC from Base, so that I don't have to acquire USDC on NEAR first.
8. As a security lead, I want to set the covered contracts, proof chain, listed tokens and prices, bounty amount, minimum theft, end date and disclosure delay, and see them read back in plain English, so that I know exactly what pays.
9. As a security lead, I want to be told plainly which contracts can and can't be covered, so that I don't post a bounty that pays out for by-design behaviour.
10. As a first-time security lead, I want a plain "what you're risking" panel before I sign, so that I know the worst case before committing funds.
11. As a security lead, I want my exploit key to come from a MetaMask signature, so that there's no file to lose.
12. As a security lead, I want to pay the posting fee and deposit the bounty in two clear prompts, so that posting is quick.
13. As a security lead, I want posting refused if a pause-role grant or pause gas is missing, so that I can't post a broken bounty by mistake.
14. As a security lead, I want to keep operating and upgrading my contracts normally while a bounty is live, so that the bounty doesn't freeze my roadmap.
15. As a security lead, I want a bug I fix myself to stop being claimable 5 minutes after the fix lands, so that I only pay for bugs that are live.
16. As a security lead, I want to see how many claims have been checked on my bounty, so that I know it's being hunted.
17. As a security lead, I want junk and AI-written claims to cost me nothing, so that I never triage again.
18. As a security lead, I want my contracts paused on every chain the moment an exploit is proven, so that nobody can use the bug while I fix it.
19. As a security lead, I want to see each chain's pause as landed and then verified on NEAR, so that I know it really happened.
20. As a security lead, I want to open the winning exploit with a MetaMask signature as soon as the Whitehat is paid, so that I can fix the bug.
21. As a security lead, I want a warning when pause gas runs low, so that I can top it up before it matters.
22. As a security lead, I want to withdraw an unclaimed bounty after its end date, so that my funds aren't stuck.
23. As a security lead, I want to be sure nobody, including BounTEE's builders, can take the bounty or pause my contracts without a proven exploit, so that granting the pause role is safe.
24. As a security lead, I want the pause role to be able to pause and nothing else, so that a false verdict can at worst pause.

**Whitehat**

25. As a Whitehat, I want `bountee init` to give me a working NEAR account with no sign-up, so that I can start in one command.
26. As a Whitehat, I want to list bounties and read each one's rules, covered contracts and trusted parties, so that I know what pays before I hunt.
27. As a Whitehat, I want to write my exploit as a Foundry script, so that I use the tool I already know.
28. As a Whitehat, I want to test my exploit locally against the contracts as they are now and see the exact verdict before paying anything, so that I never pay to learn it scores zero.
29. As a Whitehat, I want to need no paid data service, so that claiming works with ordinary public RPCs.
30. As a Whitehat, I want to top up a small claim balance once, so that claiming is quick.
31. As a Whitehat, I want my exploit sealed on my machine, so that nobody can read it, copy it or claim it before I'm paid.
32. As a Whitehat, I want to follow my claim live (sealed, checking, verdict, then pauses signed, paid, and each chain landed and verified), so that I'm not left staring at a spinner for half a minute.
33. As a Whitehat, I want my tool to deliver the signed pauses automatically after a win, so that I don't have to.
34. As a Whitehat, I want to be paid the whole bounty in USDC to my NEAR account within seconds of a verified exploit, so that there's nothing to negotiate.
35. As a Whitehat, I want a receipt with the payout, attestation and pause links, so that I can prove what happened.
36. As a Whitehat, I want a failed claim to show only a coarse reason publicly and leave my exploit unrevealed, so that a near-miss doesn't leak my work.

38. As a Whitehat, I want a Protocol fix made after my claim's block not to affect my claim, so that a Protocol can't dodge payment by racing a fix.
39. As a Whitehat, I want the first valid claim to win and a copied claim to be refused, so that nobody can steal my finding.
40. As a Whitehat, I want to never need an EVM wallet or EVM funds, so that I can win a Base Protocol's bounty without touching Base.

**Verifier (judges, the AI screen, a Protocol's community)**

51. As a Verifier, I want to check the enclave's attestation against Intel's certificates, so that I know the right program judged the claim.
52. As a Verifier, I want to rebuild the bounty contract and the judge from the repo and get the hashes that ran, so that I know the judge is the published code.
53. As a Verifier, I want to re-run a published exploit locally and get the same verdict, so that I trust nobody, not even Intel.
54. As a Verifier, I want "paused ✓" to be a fact recorded on NEAR, not just the page's word, so that the circuit breaker is provable.

57. As a Verifier, I want every README step to have a command and an expected output, so that I can follow it from a clean checkout.
58. As a Verifier, I want the README to name every trusted party and what each could do, so that the trust boundary is explicit.

**Depositor**

59. As a Depositor in a covered Protocol, I want a pause to be the worst a false verdict can do, so that my funds are never moved by BounTEE.

## Implementation Decisions

**Modules**

- **The judge.** One Rust program embedding revm, compiled once to WebAssembly and run unchanged by OutLayer in the enclave and locally under a WebAssembly runtime by the command-line tool. One build, so one attested hash. Three actions:
  - *judge a claim:* inputs are the bounty's rules, the claim's block, its state proofs (including absence proofs), the Whitehat's account and the sealed exploit (read through OutLayer's secrets). It checks the job's caller is the bounty contract and the account sealed inside the exploit matches the Whitehat's; asks the three independent RPCs pinned in its build for that chain (never from the claim or the Protocol) for the hash of the claim's block number, accepting it only when at least two answer and all match, and takes the state root from that block's header; returns INVALID if at least two agree on a different hash, or the block's timestamp is more than 5 minutes before the claim's submission time (which the bounty contract records and passes in) or after it (R2.8); fails the job with no verdict on any other outcome, such as too few answers or answers that disagree (R2.6); verifies every proof against that state root; replays the exploit from fresh accounts with the seed; scores it by the payout rule (R3.8, R4.1–R4.10); and returns PAYS, ZERO or INVALID with one coarse reason. Reads of unproven state end as INVALID.
  - *posting check:* on every covered chain, simulates `pause()` from the bounty's pause-role address, which proves the role is granted (R12.1) and the contract can be paused (R12.2), and checks the pause-role address holds enough gas for its signed pause (R7.6). It reads each chain through the same RPCs pinned in the judge's build, and fails unless at least two answer and agree (R12.5).
    - The job is `{"posting_check":{"bounty","rules"}}` (`bountee_formats::PostingCheck`) and its stdout a `PostingCheckResult`, `{"failures":[{"index","reason"}]}`: one entry per failing covered contract, by its place in the rules (an index, so all 8 fit OutLayer's output), with `cannot_pause`, `pause_gas_short` or `chain_unconfirmed`; no failures passes. The judge derives the pause-role address itself (D25) from the bounty contract pinned in its build and the MPC root key of that contract's network. It asks each pinned RPC for its head and reads at one block, the second-highest head reported, so at least two RPCs have it and none reads `latest`: the pause-role balance, each covered contract's code (an address with no code fails, since a call to it "succeeds") and an `eth_call` of `pause()` from the pause-role address with the pause's 200,000 gas limit. A read counts only when at least two RPCs answer it and every answer agrees; a JSON-RPC error saying the call reverted or ran out of gas is an answer, any other error is not. The pause gas is checked per chain for every pause there (one per covered contract): each pause's gas limit at its fee limit (0.0002 ETH) plus 0.00001 ETH for the L1 data fee an OP-stack chain such as Base charges on top (the Day-3 run on Nov 5 had a pause refused by Base Sepolia's pool holding exactly 0.0002 ETH: "want 200000000001544"), 0.00021 ETH per pause, `PAUSE_GAS_PER_PAUSE` in the shared formats and `pause_gas_per_pause` in `fees()`. Arbitrum folds its L1 cost into gas used, so there the allowance is headroom. Only Base Sepolia's RPCs are pinned so far; a covered contract on any other chain fails `chain_unconfirmed` until its three are pinned.
  - *release:* after a payout, re-encrypts the exploit to the Protocol's exploit key; after the disclosure delay, outputs it for publication together with the claim's block header and proofs, so anyone can re-run it to the same verdict at any time (R6.1, D7, D7.1).
    - The release job's input is `{"release":{"bounty","claim_id","whitehat","exploit_public_key"}}` (`bountee_formats::Release`), with the winning claim's secret. The judge checks the caller and the secret as for a claim, releases nothing for a bundle sealed for another account than `whitehat`, and writes `{"released":"<base64>"}`: the `ReleasedExploit` (`{bounty, claim_id, whitehat, exploit}`) as JSON, raw DEFLATE, encrypted to the `x25519:` exploit key as `0x01 | ephemeral X25519 public key (32) | nonce (12) | ChaCha20-Poly1305 ciphertext and tag`, keyed by HKDF-SHA256 (no salt, info `bountee-release-v1`) of the shared secret (BounTEE release v1). Randomness comes from WASI. A demo exploit's release is about 400 bytes.
  - Confirmation and replay are separate steps. In the enclave the judge always runs both; local runs (`test`, `verify`, a published exploit's re-run, the offline demo tests) replay against a recorded block header and its proofs, checking the header's hash, without RPC confirmation (R2.9). The bounty contract only ever requests the full enclave mode.
  - The replay: the exploit is the list of transactions the Whitehat's Foundry script broadcasts (`from`, `to` or `null` for a creation, `value`, `input`, `gas`; the shared formats' `Exploit`), replayed unsigned: every sender must be proven absent at the claim's block (R4.1) and starts holding the seed, nonces count from 0, and every transaction pays gas price 0, so fees never move value. It runs in the block after the claim's (number + 1, timestamp + 1, the claim block's beneficiary, gas limit and randomness, base fee 0), under Prague rules when the header has `requests_hash` and Cancun otherwise. An account no proof mentions reads as absent, and needs no proof only if it turns out to be a contract the replay created, whoever deployed it, at an address that can't have held an account before: by CREATE (its address comes from the deployer's proven nonce), or by CREATE2 from a fresh account or a contract created in the replay; its storage starts empty too (R4.5). A CREATE2 by a contract that existed at the claim's block needs a proof of the address's absence, since a reused salt lands where the chain refuses the creation; so does an account that only receives value, which is read before it exists. Attacker holdings stay the fresh accounts plus the contracts they create (R4.8): a child a covered contract deploys isn't gain. Any other unproven read is INVALID. A storage slot is proven zero by a proof of its absence or of a leaf holding zero (anvil keeps such leaves for slots a transaction only read). ERC-20 holdings are read by calling `balanceOf`, so the judge needs no token's storage layout; gain counts what the attacker holdings held at the start of the replay (the seed), so a fresh address's earlier token balance can't count as gain. BounTEE's seed is native coin only: a seed with ERC-20s can't be credited without a storage layout, so the judge refuses such a job with no verdict. Locally, the judge names each unproven read on stderr, and the command-line tool's proof fetcher (`cli/src/proofs.ts`) fetches those proofs and re-runs until none is left; in the enclave nothing is written to stderr.
  - Contains nothing specific to any exploit, contract or bounty (D11).
  - *Build:* one `wasm32-wasip2` component, because OutLayer gives HTTP only to WASI Preview 2 jobs (`wasi:http`); Preview 1 modules have no network. Input on stdin, verdict on stdout (10 MiB cap), no files or raw sockets. revm with `default-features = false, features = ["std"]` (pure-Rust precompiles; the default features pull in C crates that find no WASI sysroot), with rustc ≥ 1.91 pinned in `rust-toolchain.toml` (revm 43). The component must stay under NEAR's 1,572,864-byte transaction limit, so it uploads to FastFS in one transaction (the build with replay and block confirmation is 1.23 MB with `opt-level = "z"`, LTO and one codegen unit). It is deployed by uploading the wasm to FastFS and running it as a `WasmUrl` source with `build_target: "wasm32-wasip2"`; OutLayer testnet refuses GitHub sources. Local runs use `wasmtime run -S http judge.wasm`: the component imports `wasi:http` and won't instantiate without it, even in replay mode with no RPCs.
  - *RPCs:* Base Sepolia's three are `https://sepolia.base.org`, `https://base-sepolia-rpc.publicnode.com` and `https://base-sepolia.gateway.tenderly.co`, from independent operators, each of which answered from inside an OutLayer job (checked Nov 4). The judge needs only headers and the posting reads (`eth_call`, `eth_getBalance`, `eth_getCode`) from them; it asks for the claim's block by number, since `latest` differs between RPCs. Arbitrum Sepolia's and the mainnet chains' three are picked the same way. Jobs have no outbound allowlist (only private addresses are refused); each request times out at 30 s and a second timeout aborts the job, so the judge sets a short timeout per RPC. A Base header's hash is the keccak of its 635-byte RLP, so a recorded header is checked from its RLP.
  - *Enclave job and no verdict:* the bounty contract's input is `{"judge_claim":{rules, bounty, whitehat, block, header, proofs_json, submitted_at_ns}}` (`bountee_formats::JudgeClaim`; `proofs_json` is the proofs array as the text the Whitehat submitted, which the judge parses). The judge checks the header against the claim's hash, then recency, then asks the pinned RPCs concurrently with `eth_getBlockByNumber` (connect 5 s, first byte 10 s, so a slow RPC counts as not answering before OutLayer's 30 s cut), then replays. A job with no verdict exits with status 2 and writes nothing to stdout; OutLayer reports a non-zero exit as a failed job, which reaches the contract's callback as `null`. In enclave mode nothing is written to stderr, not even a panic message (OutLayer folds stderr into a failed job's error). The seam J tests reach local test stand-in RPCs only through a test build made with the feature `test-stand-in-rpcs`, which reads `BOUNTEE_TEST_RPCS`; the attested build is made without features and reads RPC addresses only from the table compiled into it. Proved on OutLayer testnet on Nov 4: the attested build (1,227,469 bytes, sha256 `78ff4679…0f6af2e`, one FastFS upload) confirmed Base Sepolia block 54467686 through its three pinned RPCs and replayed the claim to ZERO in 2.0 s for 0.0013 NEAR (tx `gReRLc3itnzhnxncu3yyc72YNEhKB3mzdo5xyoLTzJK`); the same job with no secret exited 2 and its result was `null` (tx `Fxg8go45N91xm6EWAdpZmXa4ZUSkFLhorLAdZjCNMrRc`).
  - *Caller and secret:* the caller check reads `NEAR_PREDECESSOR_ID`, which OutLayer sets to the account that called `request_execution`; `NEAR_SENDER_ID` is the transaction's signer and is never taken as the claimant (the claimant comes from the claim the contract records). The sealed exploit arrives as the environment variable `BOUNTEE_SEALED_EXPLOIT`. When no secret matches, OutLayer runs the job without it rather than failing it, so the judge refuses a job whose secret is missing. The bounty contract the caller must be is fixed in the judge's build (set at build time by `BOUNTEE_BOUNTY_CONTRACT`), so each deployment has its own judge build and hash. A refused job (another caller, no secret) writes nothing and exits with status 2, so OutLayer reports it failed and the contract's callback gets `null`. A bundle that can't be decoded is INVALID `malformed_exploit`; a bundle naming another account than the claim's `whitehat` is INVALID `account_mismatch` (R5.4), checked before the exploit is read. In the enclave the judge writes nothing but the verdict (R5.5). Proved on OutLayer testnet on Nov 4 against a keyless bounty contract (`b15c.b15-white-1104.testnet`): a live Base Sepolia claim filed with `bountee claim` was judged ZERO by the contract's own job (tx `JBopTCgqcKGrQH1Tg8C8Xs93FxJHej2vsB7WyRfYdAYi`); another account's direct job with the pinned build and the contract's secret was refused with "Access denied" before the program ran (`6UUViTo6VtK38DATJ2ciPJ9VZcdh7xmBt4SX3aroVShi`); the copied ciphertext filed under that account failed to decrypt with the pinned build (`5g8A4DFsrDGAR1Lgh5CkqfBVU86rPgBqrtaW4XVUgDxg`) and with another build (`BzDB7gTG9CMJScKrUarvjTf6kXJTTUe76gQJXvEUai37`); and another build given the contract's secret found none and gave no verdict (`Dtte7d974BwCYJgLkifmnmihD7uEJPf7HvxmzW3aXtf6`). A live claim's proofs run to about 120 KB, so each claim draws about 0.9 NEAR from the claim balance, mostly OutLayer's hold on input above 32 KiB, which OutLayer refunds to the Whitehat's account (not the claim balance) after the job.
- **The bounty contract.** A Rust NEAR contract with no access keys after deployment, holding many bounties. The judge's build hash is fixed at deployment, so no Protocol or claim can choose the program that opens sealed exploits or the RPCs it trusts (R1.3). Built with rustc 1.86 and cargo-near 0.20.3.
  - Post: two transactions signed in two wallet prompts: the posting fee in NEAR (posting check, storage, release and publication jobs, and each chain's pause verification; not refunded if the posting is refused), then the bounty amount as one USDC transfer-and-call (`ft_transfer_call`) carrying the rules. The rules include the Protocol's exploit public key. The bounty is live only once the posting check passes; if it fails, the USDC is refunded in full and the posting fee is not (R1.6, R11.4). A Protocol can't reuse a bounty name (D25).
    - Only one live bounty per covered contract (R12.3): `ft_on_transfer` refuses a covered contract (chain and address) that another bounty covers while its posting check is pending or while it is live and its end date hasn't passed; a bounty whose check failed frees its contracts. The callback treats anything but a `PostingCheckResult` with no failures as a failed check, including a failed job's `null`, and its `bounty_check_failed` event carries the judge's failures (or `null`) so the tool can say what to fix.
    - `ft_on_transfer` panics unless at least 100 Tgas remain, so a short-gassed posting is refunded by the token instead of holding the USDC with no check running. It requests the posting check's job, paying the job's deposit from the posting fee (`ft_on_transfer` carries no NEAR), and returns the job's promise. The callback answers the token with the amount to refund: `"0"` when the check passes, the full amount when it fails or the job fails, so the token's own resolve makes the refund (R1.6). There is no separate call to start the check.
    - The first prompt is `prepay_posting_fee` (the attached NEAR joins the Protocol's posting-fee balance, less its own entry's storage); each posting takes the flat posting fee (0.5 NEAR) from it, and nothing in it is ever paid back. The transfer-and-call's `msg` is `{"name":"<bounty name>","rules":<Rules>}`. The amount must equal the rules' `bounty_amount`; the judge hash, the 300-second recency limit and the seed must equal the contract's own, fixed in `new`. A bounty may cover at most 8 contracts and list at most 16 tokens, so its storage stays within what the fee covers.
    - Gas per hop, measured on testnet with 270 Tgas forwarded (tx `fcdYuJSbYnYWTmtbX1hnQAnGdv5bpg3GAnJx2KXHNvw`): the Ethereum RPC's relayer attaches the forwarded gas plus about 9 Tgas to `rlp_execute`; `ft_transfer_call` gets 270; Circle's USDC passes `ft_on_transfer` the prepaid gas minus about 19.5 Tgas (about 250); `request_execution` needs about 55 Tgas, 50 of them reserved for its callback. About 19 Tgas (0.002 NEAR) is burnt in all. The binding limit is wallet-selector's 270 Tgas cap on an Ethereum-wallet transaction (the relayer itself refuses more than 300 Tgas in total); the web app attaches the full 270. NEAR's own prepaid-gas cap is 1 PGas (protocol 87 on mainnet, 88 on testnet), not 300 Tgas.
  - Claim: the sealed exploit, the claim's block (number and hash), its header and proofs; the replay fee and the sealed exploit's storage deposit are drawn from the Whitehat's claim balance (R11.1), and the contract records the claim's submission time, which a retry keeps. It requests each claim's OutLayer job as soon as the claim is submitted, so judging never waits behind other claims (R11.2), and accepts verdicts only from OutLayer's contract. A job that fails or can't confirm the block leaves the claim pending in its place for a retry (R2.6).
    - The contract treats the proofs as opaque bytes, hashing and forwarding them, never parsing them. A realistic claim (a header, and proofs for 10 accounts and 30 slots of USDC's deep storage trie) is about 210 KB as JSON, or about 76 KB with deduplicated raw nodes: within NEAR's 1,572,864-byte transaction and 4 MiB argument limits, and OutLayer sets no input cap. Above 32 KiB of input, OutLayer holds a refundable 0.00001 NEAR per byte while the job is pending (1.78 NEAR at 210 KB) and reserves 50 Tgas plus 25 Mgas per byte for its callback, so the claim balance must cover that input deposit too. The whole claim path is estimated at 90–110 Tgas; carrying 210 KB into `request_execution` burnt 10.5 Tgas.
  - On PAYS: wait for every earlier-submitted claim to resolve (R3.6); request a pause signature per covered contract from NEAR Chain Signatures and check each recovers to that chain's pause-role address; store them; pay the bounty (registering the recipient with USDC if needed); then the release job is requested (see Release below). The payout never depends on a pause landing or being verified (R7.11).
    - Release: once a bounty is `paid` (the payout's transfer succeeded), anyone may call `release_exploit(id)` (`min_release_gas` in `fees()`, 85 Tgas); the payout's own callbacks have no gas to spare for a job, so `bountee open-exploit --as` asks for it. The contract requests the job itself, with the winning claim's secret profile and the exploit key from the recorded rules (no argument names a key, R12.4), holding the job deposit and the storage of the largest release (16 KiB) from the bounty's posting fee, or from NEAR attached to the call (R11.4). One release at a time (a request over 300 blocks old counts as over, and a late callback for it changes nothing); a posting whose exploit key isn't `x25519:` and 32 bytes is refused, since no release could open for it; a failed, refused or malformed job keeps nothing and can be asked again; the output is kept once and returned by the `released_exploit(id)` view. Nothing else requests a job with a claim's secret after its verdict, so a failed exploit is never released (R5.6).
    - The contract builds each pause itself from the recorded rules: an EIP-1559 (type 2) transaction to the covered contract with calldata `0x8456cb59` (`pause()`) and nothing else, value 0, an empty access list, its chain ID signed (so one pause-role address serves every chain, D25), nonce 0, 1, … per chain in rules order, gas limit 200,000, fee limit 1 gwei and priority fee 0.01 gwei, all fixed in the contract and shown by `fees()`. The fee limit times the gas limit (0.0002 ETH) is the pause gas the posting check must find (R7.6). `pause()` used 44,633 gas on a Base Sepolia fork. No method takes a payload, calldata, destination or path from a caller (R8.3).
    - The call is `sign` with `{"request":{"path":"<protocol>/<name>","payload_v2":{"Ecdsa":"<signing hash, hex>"},"domain_id":0}}`, 1 yoctoNEAR (from the posting fee) and 20 Tgas (the MPC contract asks for at least 15 and keeps 7 for its yield callback). All of a bounty's signatures are requested together and checked in one callback: s is made low (EIP-2), and the signature must recover, through NEAR's `ecrecover`, to the pause-role address. The contract derives that address itself from the MPC root key pinned in its configuration (`mpc_root_public_key`), doing the point arithmetic with `ecrecover` too (recovering (r, s) = (x, x) over −tweak·x from R = root gives root + tweak·G), and its `pause_role` view returns it for any bounty, posted or not.
    - A PAYS bounty reads `signing` until every pause is signed and stored, then `paying`, then `paid`. If any signature fails, times out (the MPC yield lapses after about 200 blocks) or recovers to another address, nothing is stored or paid; the claim stays the winner and the bounty stays closed, and anyone can call `sign_pauses` to retry (R2.5). A retry is refused while one is under way, for at most 300 blocks. The verdict's callback keeps back the gas to sign at once when the job can still get 60 Tgas; otherwise the bounty waits for `sign_pauses`. On testnet one pause was signed, checked and paid within the claim's own 300 Tgas transaction (tx `AVKLKfxwXQDaPq9JVJsi8Kr9yrZ2izCKfeau5HtgDZ4p`).
    - `bountee broadcast <protocol>/<name>` sends every stored pause with `eth_sendRawTransaction` (each chain's pauses in nonce order, all chains at once), reports a pause already sent as `known`, and with `--wait` reports each receipt.
  - Verify a pause: anyone may ask; the contract computes the transaction hash from the signed pause it stored (never taking one from the caller), calls NEAR's MPC foreign-chain transaction verification, and records a verified pause only if that transaction succeeded. The posting fee funds up to three attempts per chain; further requests pay their own cost (R7.10).
    - The call is `verify_foreign_transaction` with `{"request":{"request":{"Base":{"tx_id":"<hex, no 0x>","extractors":[],"finality":"Safe"}},"domain_id":3,"payload_version":1,"expected_payload_hash":"<hex>"}}` (outer key `"Arbitrum"` for Arbitrum), 1 yoctoNEAR and at least 15 Tgas. The contract computes `expected_payload_hash` as sha256 of `00 | 06 (Base) or 07 (Arbitrum) | tx_id (32 bytes) | 00000000 | 01 (Safe) | 00000000`, so the MPC contract accepts only a response about that exact request.
    - The callback is `#[private]`: `Ok` with a matching `payload_hash` is verified (the MPC contract has already checked the signature against its domain-3 key), and any promise failure is not. The finality is `Safe`, fixed in the contract (ADR-0015).
    - Measured on testnet (MPC contract 3.18.0): about 13.4 Tgas burnt, 0.00125 NEAR, and 7–38 s from request to verified (median 16 s). Every failure is the same timeout after about 200 NEAR blocks (about 2 minutes, 0.0015 NEAR): a reverted transaction, an unknown hash and one not yet at the requested finality can't be told apart.
  - Also: top up and withdraw claim balance; withdraw an unclaimed bounty; trigger publication; retry pause signing; read views for bounties, claims, stored signed pauses and verified pauses.
  - Each bounty's pause-role address per chain is derived from the contract's account and a per-bounty path built from the Protocol's account and the bounty's name, so it can be computed before posting.
  - Sealed exploits are stored as OutLayer secrets owned by the contract, readable only by the pinned build in jobs the contract requests (ADR-0012); the storage deposit (0.00001 NEAR per byte) comes from the claim balance.
    - The contract itself calls `outlayer.store_secrets`, since a secret's owner is whoever stores it, with accessor `{"WasmHash":{"hash":"<judge hash>"}}` and the access rule fixed in its code: `And[WasmHash(<judge hash>), Predecessor{Whitelist[<bounty contract>]}]`. No leaf names the signer, so any Whitehat account can claim.
    - One secret per claim, under its own profile (for example `c<claim id>`). The contract never stores under a profile already used: `store_secrets` silently overwrites an existing secret.
    - Jobs name the judge as a `WasmUrl` source with the judge hash and `secrets_ref {profile, account_id: <bounty contract>}`. What runs is chosen by the hash, never the URL.
    - A refused or failed job reaches the callback as a successful promise result of `null`; the contract reads it as no verdict and leaves the claim pending (R2.6). A job costs about 0.0011 NEAR (a refused one the 0.001 base fee) and reaches its callback in about 6 s.
    - Every job attaches 0.02 NEAR (resource limits 100 billion instructions, 512 MB, 60 s, estimated at 0.007 NEAR on testnet) with `response_format: "Json"` and the claimant (or, for a posting check, the Protocol) as `payer_account_id`, so OutLayer refunds what is unused to them. A claim's cost drawn from its claim balance is that deposit, OutLayer's input hold above 32 KiB, the secret's deposit (ciphertext plus 1,024 bytes) and the claim record's own storage.
    - The contract requests two enclave actions, new variants of the judge's `Job` input beside the local `replay`: `{"posting_check":{"bounty","rules"}}` and `{"judge_claim":{"rules","bounty","whitehat","block","header","proofs_json","submitted_at_ns"}}`, where `proofs_json` is the claim's proofs array as the JSON text submitted (the contract never parses it). The sealed exploit is never in the input. The seed fixed in `new` is native coin only, because the judge gives no verdict for a seed holding an ERC-20.
  - It never spends its own balance on any bounty's or claim's costs. Only one live bounty per covered contract.
  - Deployment is one transaction: deploy the code, call `new` with the configuration (OutLayer, the MPC contract, USDC, the judge hash and wasm URL, the seed) and 0.0125 NEAR to register the contract with USDC, and delete the account's only key (R2.1).
- **The command-line tool.** TypeScript on Node. Commands: `init`, list, show, test, claim, status, broadcast, verify, balance (top up, withdraw), key (add, revoke), open-exploit, withdraw (mainnet only, through NEAR Intents' 1Click), and post (the terminal fallback in the cut order). Every command has a machine-readable output mode.
  - `init` creates a local NEAR account; on testnet it is funded by NEAR's faucet service with no sign-up (D18); on mainnet it states how much NEAR to add and where.
  - `test` and `claim` run the Whitehat's Foundry script against a local fork of the proof chain at a recent block, record every account and storage slot the replay reads, fetch their proofs and absence proofs from an ordinary RPC, then run the judge locally. On a demo bounty, `test` uses the proofs committed in the repo and runs offline (D19): `bountee test --job <job.json>` replays a saved job (its recorded header, proofs and exploit) under the compiled judge with no RPC, and the demo's exploit and cheat ship as such jobs in `demo/fixtures/` (`exploit.json`, `cheat.json`: the exact inputs of the Day-3 run's claims 7 and 5, each at its own fixed Base Sepolia block). Its output names the judge build it ran by sha256 and says whether that is the bounty's pinned build; the enclave's build differs from a checkout's default build only in the bounty contract it answers to, and `--judge` runs any build. On Base Sepolia, proofs come from `sepolia.base.org`, falling back to thirdweb (`https://84532.rpc.thirdweb.com`), with one `eth_getProof` call per account because `sepolia.base.org` rate-limits bursts. The script runs as a dry run (`forge script` with no `--broadcast`) on an anvil fork at a block 3 behind the head, as a fresh random account that anvil gives the seed; its broadcast log is the Exploit, with each transaction's gas set to the block's gas limit rather than forge's estimate (forge estimates from gas used, which for a deep reentrancy is far below the limit it needs, so the replay would run out of gas; at gas price 0 the extra gas costs nothing). `test` saves the judge's exact input, the `{"replay": …}` job (default `.bountee/test/<block>-<id>.json`, or `--out`), and `claim` submits that file's block, header, proofs and exploit unchanged, so the enclave judges what `test` judged; the fresh account's key is discarded, since the replay is unsigned.
  - `claim` seals the exploit, binding the Whitehat's account, submits it, shows its progress live (D23), and on PAYS broadcasts every signed pause together, requests each pause's verification once its chain reports it final (R7.3), and gives a receipt (D24).
  - `open-exploit <protocol>/<name>` refuses until the bounty is paid, then opens the release with the Protocol's exploit key (R6.2). The key is derived from a wallet signature (D20): the Protocol's Ethereum wallet signs, with EIP-191 `personal_sign`, the fixed message `BounTEE exploit key\n\nBounty contract: <contract>\nProtocol: <protocol account>\nBounty: <name>\n\nSigning this derives the key that opens this bounty's winning exploit. It sends nothing and costs nothing.`; if two signatures match, the exploit key is the X25519 secret HKDF-SHA256(the 65-byte signature, no salt, info `bountee-exploit-key-v1`). The web app derives the same key from MetaMask. The fallback is a saved key file (`--key-file`, PKCS#8 PEM or hex). A key whose public half isn't the rules' is refused before anything is opened; `--public-key` prints the key to post.
    - Sealing: the tool asks OutLayer's keystore (`POST /secrets/pubkey` on `https://testnet-api.outlayer.ai`, mainnet `https://api.outlayer.ai`, with a `User-Agent` header) for the key of the judge hash and the bounty contract as owner, sending the secret's key names with empty values; the key depends only on hash and owner. It encrypts `{"BOUNTEE_SEALED_EXPLOIT":"<base64 bundle>"}` with OutLayer's ECIES v1 (X25519, HKDF-SHA256 with info `outlayer-keystore-v1`, ChaCha20-Poly1305), as `base64(0x01 | ephemeral public key | 12-byte nonce | ciphertext and tag)`. The bundle is the shared format `SealedBundle` (`{"whitehat":"<claimant>","exploit":<Exploit>}`) compressed with raw DEFLATE, because its storage deposit is 0.00001 NEAR per byte. The judge hash sealed to is read from the bounty contract's `config`, never from the bounty or the user.
    - "Final" means the chain's `safe` head: the tool waits until `eth_getBlockByNumber("safe")` has reached the pause's block before requesting, since an earlier request just times out and spends a prepaid attempt. On Base Sepolia the safe head lagged 11–27 minutes on Nov 4.
  - `post <protocol>/<name> --rules <rules.json> --contract <account>` signs as the Protocol's local NEAR account. The rules file is the formats' `Rules`, with the fields BounTEE sets (recency limit, seed, judge hash) filled from the contract's `config` when left out. Before spending it checks the name is unused and each covered chain's pause-role address holds the pause gas the check asks for (`--no-preflight` skips that); then it prepays the posting fee if the balance is short, sends the transfer-and-call with 270 Tgas, and reports `live`, or `check_failed` with the judge's reasons (exit status 1).
  - `verify` runs the verification layers with no keys or funds.
- **The web app.** Next.js on Vercel. Pages: landing (the finished demo bounty as a story), bounty list, bounty page, posting flow, open-exploit. Everything shown is read live from the chains and OutLayer's attestation API; the public page never shows a claim in progress.
  - Bounty page: state; rules in plain English; what doesn't pay; the number of claims judged (D22); each chain's pause as signed, landed, then verified, with a "Send pause" button for any signed pause that hasn't landed, needing no wallet (R7.9); a warning when any chain's pause gas is below what its signed pause needs (D8); Verify. Public states after the live period read "Ended, unclaimed" and "Withdrawn". After a win, the open-exploit page notes that unpausing is up to the Protocol's own governance.

**Decisions carried from the ADRs**

- Sealed and paused first, no patch window; pauses signed before payout and broadcast together; the payout doesn't wait for them (ADR-0001).
- USDC on NEAR, held by the keyless bounty contract (ADR-0002).
- Every bounty includes the pause; granting it proves control (ADR-0003).
- Build on testnet; the final demo on mainnet with a few dollars; every mainnet transaction needs Liam's yes (ADR-0004).
- Open payouts, no KYC (ADR-0005).
- One payout rule: theft from the covered contracts; one bounty amount and one minimum theft (ADR-0006).
- A prepaid claim balance for Whitehats and a prepaid posting fee for Protocols, so the keyless contract never pays anyone's costs (ADR-0007).
- Winning exploits published after a 1–90-day disclosure delay (ADR-0008).
- One proof chain per bounty (ADR-0009).
- Trust in OutLayer stated, not removed (ADR-0010).
- The cut order keeps the circuit breaker (ADR-0011).
- Sealed exploits readable only in jobs the bounty contract requests (ADR-0012).
- NEAR Intents only at the edges and only on mainnet; MetaMask sign-in for Protocols (ADR-0013).
- Claims judged against recent state, not a snapshot committed at posting (ADR-0014).
- Pauses delivered by anyone and verified on NEAR at `Safe` finality; demo chains Base and Arbitrum; no hosted watcher (ADR-0015).

## Testing Decisions

- Tests verify requirements, not code. Every test names the requirement IDs it proves; every LLR has a verification; status comes from evidence, as requirements.md's "How to read the tables" defines it. Tickets list the requirement IDs they implement; commits name their ticket.
- Tests follow Matt Pocock's `/tdd`: behaviour through public interfaces at the agreed seams, written red-then-green while each ticket is built. No tests of internals, no tautological tests.
- Seams: J (the judge, the same compiled build the enclave runs, including its posting check, run locally and offline from committed block headers and proofs, with no keys or funds), C (the bounty contract in a local NEAR sandbox, with stand-ins for OutLayer and the MPC network, including its foreign-chain verification; the stand-ins answer with success and failure alike, including failures testnet can't trigger at will, live only in the test folder and are named as test stand-ins), T (the command-line tool, driven by committed scripts on testnet, chain state read back with `cast` and NEAR RPC), W (the web app, driven by committed Playwright specs in a browser), E (the demo contracts with Foundry).
- That the real services behave as the seam C stand-ins assume is proven at seam T (R3.10, R4.11, R7.4, R7.10). Mainnet-only features (D12, D16) are verified by a recorded mainnet run under Liam's yes.
- The full two-chain run happens at the Day-3 checkpoint, at demo-ready and before the video; day to day uses J, C and T on one chain; a setup script reports every balance a run needs and stops before starting, naming what to top up, if any would run dry. One mainnet pass of the end-to-end tests runs before the demo, with Liam's yes.
- The repo is greenfield; there is no prior art in it.

## Out of Scope

- Pre-launch code with nothing live to pause.
- Covering contracts that pay callers by design (AMM pools, lending with liquidations, keeper rewards).
- Bugs where nobody profits (freezing, denial of service, insolvency), protocol-written invariants, multi-block or time-dependent attacks, attacks needing a victim's later transaction, theft of users' approvals.
- Bugs that exist only in one chain's configuration.
- More than one payout per bounty, payout tiers or scaling by funds at risk, top-ups.
- Non-EVM chains (including Solana) and EVM chains the MPC network can't verify (including Flare and Ethereum).
- A hosted watcher.
- KYC'd payouts, sponsored claims, a web claim screen (unless the Day-3 checkpoint passes with time to spare).
- A bug-finding AI agent of our own; NEAR AI Cloud; NEAR Intents anywhere except the mainnet-only `withdraw` and "Fund from Base"; choosing the payout chain at claim time.
- Accounts, profiles, notifications, leaderboards, search, editing a bounty, dispute screens.
- Insider fraud (a Protocol member planting and claiming a bug), as on any bounty platform; the README's threat model says so.
- Verifying the TDX quote inside the bounty contract.
