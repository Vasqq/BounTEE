# A claim can be proven on any covered chain

ADR-0009 had each bounty name one proof chain, so a bug that exists only in a Protocol's Arbitrum deployment could never win, though the pitch is that one keyless rule on NEAR guards every chain. A Protocol on Base and Arbitrum expects a bug on either to pause both, and can't pick one chain well. So each claim names its own proof chain, which may be any covered chain: the claim's block is that chain's, the judge confirms it with that chain's pinned RPCs (the same ones the posting check already reads, R12.5), loss counts only the covered contracts on that chain, and a win still pauses every covered contract on every chain.

## Decisions

- **The claim names its chain in its block reference** (chain, number, hash), because a block number means nothing without its chain. The bounty contract refuses a claim on a chain the bounty doesn't cover before drawing anything from the claim balance; the judge also returns INVALID for one. A header from another chain can't pass confirmation, since that chain's RPCs answer with their own block's hash.
- **How a chain is judged comes from the chain, not from its header's shape.** Until now the judge refused any header with fewer fields than Ethereum's at its Shanghai upgrade, and guessed the EVM rules from whether the header carried Ethereum's newest field. Both follow Ethereum's upgrade history: Base copies Ethereum's header layout, so it passed by coincidence; Arbitrum's headers stop at the base fee and its EVM upgrades don't change them, so every Arbitrum claim was refused, and none had ever been proven. Now three layers each do one job: the header's hash, confirmed by the chain's pinned RPCs, says the block is real (unchanged, and the same on every EVM chain); the judge reads from the header only the fields the replay needs, which every EVM header shares; and a chain profile says how the chain executes. Profiles are one table keyed by chain ID, compiled into every judge build whatever network it pins RPCs for, so a checkout's local build replays a mainnet chain exactly as the enclave does (D2). A profile gives the EVM rules, the per-transaction gas cap, the randomness the chain returns and the fewest header fields it accepts. A chain with no profile replays exactly as before (at least Shanghai's 17 header fields; Prague when the header has `requests_hash`, Cancun otherwise), so Base, Ethereum and local test chains don't change. Arbitrum One and Arbitrum Sepolia, both on ArbOS 61 (read Nov 8), get Osaka's rules with Arbitrum's 32,000,000 per-transaction gas cap (read from the chain, not Ethereum's 16,777,216), randomness 1 (what Arbitrum's `PREVRANDAO` returns; its header's mix hash is not randomness) and 16 header fields. The judge clamps each replayed transaction's gas to its chain's cap: at gas price 0 the gas costs nothing, and a transaction that needs more would fail on the chain too. The profile is in the build, not the rules, so no Protocol chooses how its chain is judged (R1.3).
- **A chain can be proven on when** its headers hash the Ethereum way, its state is an Ethereum-style Merkle-Patricia trie served by `eth_getProof`, and it has three independent public RPCs; pausing it also needs NEAR's MPC network to sign and verify there. Adding one is a profile entry, three RPCs and a test on a recorded real block. Chains with other state proofs (zkSync, Linea) would need their own proof module.
- **Remaining differences are stated, not emulated (R15.7):** Arbitrum's block-number opcode returns an L1 block number, and its system contracts and Stylus (WebAssembly) contracts don't exist in the replay, so a contract that relies on them may replay differently from the chain. Base already runs Osaka's opcodes but is still replayed under Prague, as before; giving Base a profile would change verdicts on the chain the demo already runs on, days before the deadline, so it waits. The profile is where each fix would go.
- **Each listed token names its chain**, so the rules show exactly what is valued on each chain. A posting is refused if a listed token is on a chain the bounty covers no contract on, or if a covered chain has no listed token (a theft there could never score).
- **The seed is unchanged:** native coin only, given to fresh accounts on whichever chain the claim is proven.
- **One minimum theft**, in value units, applied on whichever chain the theft is proven.
- **Recency and confirmation are unchanged** (ADR-0014), applied to the claim's chain.
- **"Judged once" stays per sealed exploit** (R3.5). Sealing is randomised, so a Whitehat trying another chain seals again; the rule only stops the same bytes being filed twice.

## Considered Options

- **Keep one proof chain:** the smallest scope, but it leaves a per-chain bug unwinnable, the first question a judge will ask.
- **A table of each chain's USDC built into the judge:** fewer fields in the rules, but it puts token knowledge in the judge (D11) and makes WETH or any other token a new judge build. Naming the chain on each listed token keeps the judge generic and the rules complete.
- **Every chain's state in each claim:** would judge an exploit across chains at once, but a cross-chain exploit isn't one replay, and every claim would carry proofs for every chain.

## Consequences

- For the hackathon each chain lists only its own USDC at price 1. Other tokens (WETH and the like) are future work that needs no format change.
- The bounty contract pins its judge build and holds no keys, so `bounty.bountee.near`, deployed on mainnet on Nov 7 with the one-proof-chain judge, can't take this change. It needs a new mainnet deployment on a new account, `bounty2.bountee.near`, about $23 more, which takes the spend past ADR-0004's $50 (Liam's yes, Nov 8). `bounty.bountee.near` stays as it is, unused. This reverses spec #48's reuse of `bounty.bountee.near` for the demo rerun.
- The demo shows both chains judged: the cheat claim is proven on Base and scores zero, and the AI agent's winning claim may be proven on either chain, pausing the other too. The demo vault holds 2 USDC on each chain (Liam, Nov 8), so a theft on either can reach the 1 USDC minimum theft, and the rule holds on the demo bounty itself: 4 USDC at risk instead of 3.
- The web app's Proof chain field goes in the same change as the bounty contract and judge, not before: until both accept any covered chain, removing it would silently make the first covered chain the only one that can win.
- Cut-off: if this isn't ready for mainnet by the end of Mon Nov 9, it doesn't merge: the demo runs on `bounty.bountee.near` with one proof chain and the vault back at 2 USDC on Base and 1 on Arbitrum, ADR-0009 stands, and the README discloses that only Base claims can win.
- Supersedes ADR-0009. Amends ADR-0004 (the spend), ADR-0018 (the demo's chains) and ADR-0019 (the vault's funding per chain).
