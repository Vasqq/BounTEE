# Only wallets that can sign everything a Protocol signs

MetaMask was ADR-0013's example wallet, not a choice, and not every Protocol uses it (Liam, Nov 12). The web app now connects through RainbowKit's wallet picker, but a wallet is offered only if it can sign everything the Protocol wallet signs, because a wallet that fails partway strands a Protocol mid-posting, or worse, can't reopen the exploit key it posted with. Each wallet must hold a plain key (no smart account, which NEAR can't use), send plain transactions on the covered chains, add and switch to NEAR's Ethereum-compatible chain (397 or 398) and send there, and `personal_sign` deterministically (RFC 6979), since the exploit key is derived from that signature and must come out the same months later (D20). So the picker shows exactly MetaMask, Rabby and Zerion as browser extensions, Brave Wallet in the Brave browser (where RainbowKit shows it), and MetaMask Mobile by QR code through WalletConnect; every other wallet is hidden, including ones the browser announces as installed (EIP-6963), with one line saying only wallets that can sign on NEAR are shown (Liam, Nov 12).

## Evidence

Each listed wallet was checked against its own source on Nov 12 (notes kept with the session; key sources below). Nothing was tested hands-on yet. Each wallet's handling of NEAR's chain (397/398) and of the 1-wei relayer-key transaction is unconfirmed except MetaMask's; a recorded testnet run with a real Rabby (D35) and a real MetaMask Mobile (D36) follows this change. That run is on the testnet site and counts as evidence, an exception to ADR-0017's rule: the testnet and mainnet builds differ only in the network table's values (ADR-0021), so a wallet's behaviour is the same on both, and a mainnet posting would lock real USDC for nothing more (Liam, Nov 12).

- **MetaMask:** signs through `@metamask/eth-sig-util`, which ends in noble's RFC 6979 signing; keeps a site's legacy `gasPrice` on chains without EIP-1559 (`MetaMask/core`, transaction-controller `gas-fees.ts`); NEAR's own module carries a MetaMask-specific workaround, the only wallet-specific code in it. MetaMask Mobile approves `wallet_addEthereumChain` over WalletConnect; that it signs through the same `eth-sig-util` is likely but not traced.
- **Rabby:** `eth-simple-keyring` signs through the same `eth-sig-util`; an unknown chain is added from its add-chain dialog as a custom network.
- **Brave Wallet:** signs with libsecp256k1's `secp256k1_nonce_function_rfc6979` (`brave-core`, `hd_key.cc`); implements `wallet_addEthereumChain`.
- **Zerion (extension only):** signs with an ethers v6 signer (noble, no extra entropy); implements `wallet_addEthereumChain`, and testnet chains need its testnet mode. Zerion's phone app is unconfirmed, so its entry never falls back to WalletConnect.
- A Ledger works when used through MetaMask or Rabby (its Ethereum app signs messages with RFC 6979), not through Ledger Live.

NEAR's own Ethereum-wallet module names no list beyond MetaMask and WalletConnect, and excludes smart accounts. Its one free transaction (the relayer key) is sent at a 1-wei gas price; a wallet that substitutes its own price only charges a little more NEAR, which the account already holds at that step.

## Considered Options

- **RainbowKit's default list:** includes Coinbase's smart wallet (Base Account), Rainbow and any WalletConnect wallet. Smart accounts can't sign on NEAR, and Rainbow mobile and Ledger Live refuse NEAR's chain over WalletConnect.
- **Every installed wallet, tested at runtime:** a wallet would fail only after the Protocol had granted pause roles on one chain. The sign-twice check (D20) stays as a backstop, not the gate.
- **Coinbase Wallet (plain-key mode), Trust and OKX:** closed source, so neither deterministic signing nor NEAR's chain could be confirmed. Left out until a hands-on test proves them (Liam, Nov 12).
- **Phantom:** can't add custom chains and doesn't support Arbitrum.

## Consequences

- Amends ADR-0013's "Protocols sign in with MetaMask": they sign in with the Protocol wallet, any wallet this ADR lists. Its other consequences hold for every listed wallet.
- Every build needs a WalletConnect (Reown) project ID: RainbowKit's MetaMask entry falls back to WalletConnect when its extension is absent, and RainbowKit throws without one. RainbowKit's stock Zerion entry would fall back too, offering an unconfirmed phone wallet, so Zerion is an extension-only entry built with RainbowKit's custom-wallet API. RainbowKit is pinned to an exact version for the same reason. The ID is public by design, restricted to the sites' origins in Reown's dashboard, set in each site's build settings, and kept out of the repository; a build without it fails rather than shipping a picker that crashes.
- The picker can't see a wallet the browser only announces (EIP-6963 discovery is off, the one RainbowKit setting that keeps the list exact), so a listed wallet is found by the flags it sets on the page's injected provider. The list is therefore enforced by provider flags, not by wallet identity: a wallet that sets MetaMask's flag and none RainbowKit knows as an impostor's would be offered as MetaMask. With two listed extensions installed, the one that owns that provider may answer for both; D35's real run checks MetaMask and Rabby side by side, and passes if the account the flow shows is always the picked wallet's.
- MetaMask's entry is built with RainbowKit's custom-wallet API too: the stock one's MetaMask SDK calls the wallet at page load, and a stock WalletConnect connector contacts WalletConnect at page load, where BounTEE's signing pages ask nothing of a wallet before a click (D13, D36). It uses an injected connector on the provider RainbowKit's own MetaMask check accepts, so the entry's "installed" test and its connector reject the same impostors, and RainbowKit's WalletConnect connector when it isn't. RainbowKit doesn't export that check, so the entry carries a copy of its impostor flags, kept in step with the pinned RainbowKit version.
- Each build's check that it sends none of the other network's values (D30; and for the mainnet build, no "testnet" word, D4, ADR-0017) stays in full on every page's HTML and every script a public page loads. WalletConnect's code that RainbowKit never runs (Reown's own modal) is left out of the build. If RainbowKit's or WalletConnect's remaining chunks, loaded only on the signing pages, still name the other network's chains in their own chain lists, those chunks are checked instead for the other network table's own values that are BounTEE's alone (its bounty contract, USDC, MPC root key and NEAR Ethereum RPC): each build still reads, links and signs only its own network's.
- Neither `/post` nor the open-exploit page reconnects a WalletConnect session on reload: `/post` reconnects only the browser-extension wallets, so WalletConnect starts only when the Protocol picks MetaMask Mobile (D36). A Protocol on MetaMask Mobile scans again after a reload. In a phone browser, MetaMask's entry hands off to the MetaMask app by its WalletConnect deep link.
- Adding a wallet later means checking it against the four conditions above from its own docs or source, or a recorded hands-on test, and amending this ADR.
